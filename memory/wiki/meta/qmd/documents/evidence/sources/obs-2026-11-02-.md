# ⭐ Observation: 虚拟摄像头打通：接收端先行握手+分辨率限制+三次假阳性教训

虚拟摄像头全链路实测打通（2026-11-02）：UnityCapture(MIT)驱动注册为"LiveStudio Cam"(HKCU免管理员)，协议=共享内存UnityCapture_Data0+Mutx0/Sent0/Want0握手，pyvirtualcam(unitycapture后端pyd)与驱动同名兼容。三个关键教训：①黑屏根因是测试时序——pyd只有OpenFileMappingA(只开不建)，必须接收端(平台)先开摄像头建共享内存，发送端后启；②之前"E2E通过"是假阳性（黑帧也能编码出MB级文件），必须抽发送期间的帧验颜色；③mp4录制在发送端关闭时驱动断流卡死ffmpeg→moov缺失，改用select=gte(n,90)+frames:v 1单帧截取。分辨率限制：UnityCapture源码表仅22种横屏规格(16:9/4:3/16:10，含1920x1080/3840x2160)，无1080x1920竖屏；滤镜内置BGRResizeLinear等比居中缩放→竖屏素材在平台侧=1920x1080带左右黑边(实测720x1280发送avg(37,25,37)符合三成面积 pillarbox 计算)。LuBot TK Cam原生竖屏因其LuBotCam.dll自研——不复制其专有驱动(属其代码)，用MIT驱动等效替代。v2.0应用级闭环：UI开关→ffmpeg rawvideo子进程→pyvirtualcam→平台收到素材帧(云层画面可见)。
